## Context

The live v0.1 site (`lib/tokens.ts`, `app/page.tsx`) is dark-mode-first (near-black/indigo base, gold/amber accent), with a homepage hero of "Ecclesia Lucis" (eyebrow) → "The Church of Light" (tagline) → "A faith of equals" (`<h1>`), identity statement and "what this is not" disclaimer both above the fold, followed by a repeating 2-column `doctrineTeasers.map(...)` card grid and a closing `CtaBanner`. `web-v0-2-redesign` proposed (but never applied) a light-mode-first, spectrum-accent palette plus two new motifs (spectrum-bleed edge glow, wayfinding-thread) and a hero-only restructure — its palette-token engineering (`spectrumAccent1..6`, theme-role-swap, AA contrast targets) is sound and is reused here. See `docs/design/v0-3-radical-light-vision.md` (the full creative brief this change formalizes) and `proposal.md` for the "why" behind going further than v0.2.

## Goals / Non-Goals

**Goals:**
- Formalize `docs/design/v0-3-radical-light-vision.md`'s decisions (true-white base, edge-bleed, full-length wayfinding thread, near-silent hero, chapter-based homepage, optional particle layer) into buildable spec/design/task artifacts.
- Reuse v0.2's palette-token engineering pattern rather than re-deriving it, re-tuned for a true-white base.
- Keep every `CLAUDE.md` content rule and `docs/PRD.md` §5 accessibility/performance requirement intact, except the one explicitly flagged open decision (REQ-HOME-001 placement), which stays unresolved until the founder signs off.

**Non-Goals:**
- No doctrine copy changes, no route changes, no CTA destination/copy changes.
- No photography or illustration work (still out of scope per `docs/CONTENT_STRATEGY.md`).
- The particle/WebGL enhancement's exact visual parameters (mote count, drift speed, bloom radius) are an implementation-time judgment call within the "drift and bloom only, never strobe" constraint — not specified numerically here.
- Not re-litigating v0.2's non-hierarchy/non-pride-flag framing decision (`web-v0-2-redesign/design.md` Goals/Non-Goals) — it carries forward unchanged: the spectrum motif stays abstract ("light's full spectrum"), not literal pride iconography.

## Decisions

**Supersede v0.2 by archive-note, not by applying it first.** Move `openspec/changes/web-v0-2-redesign/` to `openspec/changes/archive/` with a one-line superseded note, without running `/opsx:apply` on it. Rationale: v0.2's hero decisions (identity statement above the fold, "Church of Light" as `<h1>`/largest element, hero-only motion) are directly contradicted by v0.3 (near-silent hero, "Ecclesia Lucis" as the largest/most kinetic element, full-homepage motion). Applying v0.2 first would mean writing code only to immediately restructure it again. Alternative considered: apply v0.2, then layer v0.3 on top — rejected per the vision doc's own recommendation (§3) and because it wastes a full build cycle on code that gets replaced within the same session.

**Reuse v0.2's token *shape*, replace its *values*.** Keep the `spectrumAccent1..6` + single `accent` fallback token structure from `web-v0-2-redesign/design.md`'s "Palette shape" decision (discrete hues for text/icon use where a gradient can't apply) and the theme-role-swap approach (`lightTheme` at `:root` by default, `darkTheme` behind `prefers-color-scheme: dark`, both themes keep the full token set so no component branches on active theme). Only the concrete hex values change: base goes from v0.2's off-white draft to true white/near-white (`#ffffff`–`#fdfdfb`), which increases base contrast headroom (~21:1 vs v0.1's dark ~15:1) rather than decreasing it, so re-tuning the six spectrum hues for 4.5:1 text / 3:1 large-text-and-icon contrast against a whiter base is a strictly easier constraint to hit than v0.2's off-white version.

**Hero heading semantics: "Ecclesia Lucis" becomes the largest, most kinetic element; "The Church of Light" is smaller and appears first.** This inverts v0.2's decision (which made "Church of Light" the `<h1>`/largest element) per the founder's v0.3 brief (§1 point 8, §4.4). `<h1>` = "Ecclesia Lucis" (the actual proper name, now both visually and semantically primary); "The Church of Light" renders above it as a smaller, non-heading label. This keeps single-`<h1>`/logical-order semantics intact while matching the founder's explicit size order for v0.3, same pattern v0.2 used to reconcile accessibility semantics with visual hierarchy.

**No pronunciation guide carried forward from v0.2.** v0.2 added a pronunciation guide beneath "Ecclesia Lucis" as a warm, disarming detail. The v0.3 brief is explicit that the first screen contains only the two name lines and "then nothing" (§1 point 8, §4.4: "It should not move again on scroll; the drama is the arrival") — no room is specified for a third line in that first screen. Not carrying it forward is a minor, non-scope-changing assumption (the brief doesn't mention it either way); it can be reintroduced in "the turn" chapter later if the founder wants it back, but this change doesn't add it there since the brief doesn't call for it.

**REQ-HOME-001 content moves to "the turn," not dropped — but shipped as a proposed resolution pending sign-off.** Per `proposal.md`'s Open Decision: the identity statement and "what this is not" disclaimer relocate to the chapter immediately following the hero (vision doc §5 step 2), reachable with one scroll, no click. This is the vision doc's own recommended fix (§7 item 1). The spec delta encodes this as the target behavior so `design.md`/`tasks.md` are coherent and buildable, but `tasks.md`'s relevant tasks are marked as blocked on founder sign-off (see Migration Plan) rather than silently treated as approved.

**Chapter layouts as data-driven distinct components, not a single parameterized "teaser" component.** The current `doctrineTeasers.map(...)` card grid is a single component rendering four near-identical cards. v0.3 needs four *visually distinct* treatments (left-aligned+graphic, right-aligned+graphic, expanding-text-box, pull-quote), so this change introduces one component per layout pattern (reusing `components/PullQuote.tsx` for Covenant, adding a new expanding-text-box component for Practices, and two graphic+text layout variants for Purpose/Tenets — likely one component with a `flip`/`align` prop rather than two separate components, since the only difference is left/right mirroring) rather than forcing all four into one generic "teaser" abstraction. Alternative considered: one highly-parameterized `DoctrineChapter` component handling all four variants via props — rejected because the "each section feels different" brief goal is easiest to guarantee by construction when the layouts are genuinely different JSX trees, not variations of one template fighting to look distinct.

**Scroll reveals via CSS `animation-timeline: view()`/`scroll()`, static fallback, no scroll-jacking JS.** Carries forward v0.2's wayfinding-thread approach and extends it to every chapter reveal and the expanding-text-box interaction. Per the vision doc §2's research grounding: ~84% global support mid-2026, runs on the compositor thread, and degrades to fully-visible/fully-expanded static content on unsupported browsers — never a hidden or broken state. Alternative considered (a JS `IntersectionObserver`-driven reveal library): rejected as unnecessary weight/risk for decorative reveals, consistent with v0.2's own rejection of scroll-jacking JS for the thread motif.

**Particle layer: dynamically imported, hero-scoped, gated on four conditions.** A canvas/WebGL component loads only when: viewport is above a defined breakpoint, a pointer (not touch-only) is detected, `prefers-reduced-motion` is not set to reduce, and `navigator.connection.saveData` is not true (with a safe default of "don't load" if the Save-Data signal is unavailable rather than assuming permission). It is dynamically imported (`next/dynamic` with no SSR) so its JS cost is zero on non-qualifying devices and it never blocks the hero text's paint (the text remains the LCP element regardless of whether the particle layer loads). Alternative considered: always render a lighter-weight CSS-only particle simulation instead of gating a canvas layer — rejected because the vision doc explicitly scopes this as an optional, device-tiered enhancement, not a universal requirement, and forcing a lighter version everywhere reintroduces the "cost on every device" problem the gating is meant to avoid.

## Risks / Trade-offs

[Near-silent hero ships without founder sign-off on the REQ-HOME-001 placement, and the founder disagrees after seeing it built] → Mitigation: flagged explicitly in `proposal.md` before any code is written; `tasks.md` marks the hero-restructure and "the turn" relocation tasks as blocked on that sign-off, so implementation can pause at exactly that boundary rather than shipping the whole homepage and needing a second full pass.

[Four genuinely different chapter layouts cost more implementation time than one parameterized teaser component, and drift out of visual sync over time as content changes] → Mitigation: all four still consume the same underlying doctrine copy data and the same design tokens (`spacing.chapter`, spectrum accents, typography scale) — only the JSX structure differs, so a future content change (not a redesign) stays a one-line data edit per chapter, not a template rewrite.

[Scroll-driven CSS animation support gaps (~16% of global traffic per the vision doc's own estimate) show static content for a meaningful minority] → Mitigation: this is the same trade-off v0.2 already accepted for the thread motif — "degraded but present" (fully visible/expanded) is an acceptable fallback for purely decorative motion, never a broken or missing state; explicitly required by the design-system spec's scenario coverage.

[Particle layer becomes a performance or Core Web Vitals regression despite gating] → Mitigation: dynamic import with no SSR, hero-scoped only, gated on four conditions before any bytes are fetched; `tasks.md` includes an explicit Core Web Vitals re-check against `docs/PRD.md` §5 budgets before calling the particle task done, and the layer must ship as a stretch task — if it threatens the budget, cutting it entirely is an acceptable resolution, not a blocker for the rest of the change.

[Bright spectrum accents on a true-white base read as garish if overused, more than on v0.2's softer off-white] → Mitigation: same targeted-use restriction v0.2 specified (links, icons, small fills, the two decorative motifs; never full-bleed color blocks) carries forward unchanged; design review against the built pages before calling this done, per `CLAUDE.md`'s "verify UI changes in a browser" rule.

## Migration Plan

1. Move `openspec/changes/web-v0-2-redesign/` to `openspec/changes/archive/` with a one-line superseded note (per the Decisions section above) — first task, unblocks nothing else but should happen before token work starts so there's no ambiguity about which proposal is authoritative.
2. Replace `lib/tokens.ts` values: true-white base, near-black ink, re-tuned `spectrumAccent1..6`, new `spacing.chapter` token — reusing v0.2's token shape.
3. Update wherever theme CSS variables are emitted (`tailwind.config.ts` or equivalent) for the new values and the new spacing token.
4. Re-tune the spectrum-bleed edge-glow treatment for the whiter base; build `components/WayfindingThread.tsx` (new, since v0.2 never shipped it) sized for full-homepage length; add the kinetic-type load-in keyframes for the hero wordmark.
5. **Pause point — do not proceed past here without founder sign-off on the REQ-HOME-001 placement decision** (per `proposal.md`'s Open Decision). Once sign-off is received:
   a. Restructure `app/page.tsx`'s hero to the near-silent form.
   b. Build "the turn" chapter carrying the relocated identity statement and disclaimer.
   c. Build the four distinct doctrine chapters (Purpose, Tenets, Practices, Covenant) replacing the card grid, each wired to the wayfinding thread and its scroll-reveal behavior.
6. Optional/stretch: build the device-tiered particle layer behind the hero, gated per the Decisions section; verify it never regresses Core Web Vitals or delays hero text paint.
7. Manually verify in a browser (per `CLAUDE.md`): both themes, `prefers-reduced-motion`, contrast spot-checks on spectrum-accent text/icon usages, and the doctrine-before-CTA ordering, before calling the change done.
8. Update `docs/CONTENT_STRATEGY.md` Brand Direction section to describe the v0.3 direction as superseding both v0.1 and the never-shipped v0.2 draft.

No rollback complexity beyond a normal revert — this is a static-site presentation-layer and homepage-structure change with no data migration.
