## Context

The current homepage (v0.3, `app/page.tsx`) is a near-silent hero followed by a fixed sequence of card/chapter components (`GraphicTextChapter`, `ExpandingText`, `PullQuote`) revealed via CSS `animation-timeline: view()`/`scroll()`, stitched together by a decorative `WayfindingThread` SVG and a bright spectrum-accent palette (`lib/tokens.ts`). This change replaces that structure and palette with the design validated in a standalone HTML/CSS/JS prototype (Artifact: https://claude.ai/code/artifact/ce09f655-a52f-4258-9848-75cc12605968), iterated live with the founder across three rounds: an initial build, a fix for a broken reveal animation, and a fix for duplicated section text. The prototype's technical lessons (below) are load-bearing, not incidental — they were each found by shipping something that visibly failed, not by first-principles design.

`docs/PRD.md` REQ-HOME-001 (identity statement above the fold) and REQ-NAV-001 (persistent navigation) were already amended by the founder on 2026-08-29 specifically to clear the way for this design; `openspec/specs/marketing-pages/spec.md` and `openspec/specs/site-scaffold/spec.md` reflect those amendments already, prior to this change's own deltas.

## Goals / Non-Goals

**Goals:**
- Specify the threshold-reveal mechanism precisely enough that it doesn't regress into the prototype's first broken version (SVG `<mask>` + filter, silently non-repainting).
- Specify the label/content split precisely enough that it doesn't regress into the prototype's second bug (same sentence shown twice).
- Resolve the two decisions the founder left to this change's judgment: `WayfindingThread`'s fate, and whether interior pages get the full pinned-scroll treatment.
- Specify a concrete, accessible equivalent for the pointer-near-top navigation trigger, since it has no analog for touch or keyboard-only visitors.

**Non-Goals:**
- Pixel-level visual polish (exact easing curves, mote scatter algorithm tuning, precise color values beyond the two anchor tones) — left to implementation and visual QA, not spec-level detail.
- Rewriting doctrine copy — content is unchanged, only its presentation.
- Extending the pinned-scroll treatment to interior pages (explicitly decided against, see Decisions).
- Rebuilding `Nav.tsx`'s mobile menu interaction pattern beyond what's needed to add the reveal/hide behavior — the existing mobile menu toggle is reused.

## Decisions

**Threshold reveal: CSS `mask-image: radial-gradient()` recalculated on scroll, not an SVG `<mask>` + filter.** The prototype's first implementation used an SVG `<mask>` element (with a `feTurbulence`/`feDisplacementMap` filter for a rough, dust-like edge) referenced via `mask: url(#id)`, with the mask's circle positioned in percentages and no `viewBox` on the host SVG. This rendered as a hard cut from one state to the other instead of a growing circle — most likely because percentage-based coordinates inside an SVG mask referenced from CSS have no reliable frame of reference without an explicit `viewBox`, and/or the mask+filter combination wasn't being repainted on every attribute change. Swapping to a plain CSS `mask-image: radial-gradient(circle Rpx at 50% 50%, #000 innerPx, transparent Rpx)`, with `R` and `inner` recalculated and written to the element's inline style on every scroll frame, fixed it immediately and reliably. *Alternative considered:* keep the SVG mask but add a `viewBox` and fix the coordinate system — rejected because the plain CSS approach is simpler, has no cross-browser mask+filter interaction risk, and the rough dust-edge texture (the reason for the SVG filter) can be approximated later with a feathered gradient stop instead, at much lower risk. The precise dust-edge texture is left as a visual-polish decision for implementation, not a spec requirement.

**Threshold reveals a label only; the chamber reveals the real content, once.** The prototype's second bug was duplicated text: the growing circle originally revealed the section's full heading and body sentence, and then the chamber immediately below — now in normal document flow — showed the identical sentence again as its "static" opening, since the reveal-and-release technique requires the sticky panel's final frame and the next section's first frame to match. The fix was to split responsibility: the threshold reveal shows only a short label (e.g. "Purpose"), and the chamber's heading/body fade in afterward via `IntersectionObserver` as the visitor scrolls into the chamber. This is now a spec-level requirement (`design-system`: "Iris threshold-reveal mechanism", scenario "Threshold reveal shows only a label, not the chamber's full content") specifically so a future implementation doesn't quietly reintroduce the duplication by copying the reveal-and-release technique without also copying this constraint.

**Retire `WayfindingThread`.** Read `components/WayfindingThread.tsx`: it is a full-homepage-length SVG line rendered in the retired `spectrumAccent1..6` gradient, explicitly built to stitch together the v0.3 chapter layout it ran behind. Under Threshold, there is no chapter layout for it to run behind, no spectrum-accent palette for it to render in, and the threshold-reveal mechanism itself already provides the "one continuous path" function the thread existed for. Keeping it would mean maintaining a component with no visual role and a palette dependency on tokens this change also retires. *Alternative considered:* re-skin it in the paper/void/ember palette and run it behind the chamber sequence — rejected as pure decoration competing with the iris-reveal for visual attention, which the founder's own framing ("invite discovery through subtlety") argues against layering on more motion, not less.

**Interior pages get the visual system, not the pinned-scroll mechanism.** Applying the full hero-plus-iris-reveal treatment to every route would force a visitor who navigates directly to `/covenant` from a search result or shared link to scroll through an unrelated hero and threshold sequence before reaching the content they came for — a usability regression with no offsetting benefit, since the "discovery through subtlety" framing is specifically about the homepage's first-visit journey, not about gating return visits or deep links. Interior pages instead adopt the paper/void/ember palette, Odibee Sans/DM Sans typography, and scattered-mote content pattern directly, rendering immediately like any normal page. *Alternative considered:* give every page its own single threshold flip on load — rejected for the same reason at smaller scale: it still delays content for a visitor who didn't ask for a journey, just an answer.

**Navigation's accessible equivalent: end-of-scroll reveal, plus an early-tab-order focusable control.** The founder's decision (reveal on end-of-scroll OR pointer-near-top, hidden otherwise) is pointer-and-scroll-shaped; neither trigger is naturally available to a touch visitor (no hover) or a keyboard-only visitor (no pointer position at all) partway down a page. Rather than leaving those visitors unable to reach navigation except by scrolling all the way to the bottom, the spec (`site-scaffold`: "Context-triggered primary navigation") requires a keyboard-focusable control reachable early in the tab order that reveals navigation on focus — concretely, a visually-minimal "skip to navigation" style control, not a persistent visible bar, so it doesn't reintroduce the fixed-chrome look the founder is moving away from. *Alternative considered:* rely on end-of-scroll alone as the universal fallback — rejected because it forces every non-pointer visitor to scroll an entire long page before reaching Purpose/Tenets/etc., which is a materially worse experience than a discoverable focus-triggered control, and REQ-NAV-001 requires navigation be reachable on every page, not just after reading it end to end.

## Risks / Trade-offs

- [Risk] A near-silent hero with no visible navigation could read as "broken" or "stuck" to an impatient visitor on first load. → Mitigation: the hero's own load-in sequence ends with an explicit scroll affordance (already a spec requirement); this is a continuation of v0.3's existing near-silent-hero pattern, not a new risk introduced by this change.
- [Risk] `mask-image` recalculated on every scroll frame via inline style writes could cause jank on low-end devices if not throttled. → Mitigation: gate the recalculation on `requestAnimationFrame`, matching the prototype's approach, which measured acceptably smooth; treat this as an implementation/performance-pass concern (`docs/ROADMAP.md` Phase 2), not a spec-level requirement.
- [Risk] Retiring the entire spectrum-accent/dark-mode system is a second full palette replacement in two weeks (v0.1 → v0.2 draft → v0.3 → Threshold), which could read as design thrashing to anyone reviewing git history. → Mitigation: this is a founder-directed, explicitly confirmed decision (not an agent guess), and `docs/CONTENT_STRATEGY.md`'s "Concept history" line already documents the succession honestly rather than hiding it.
- [Risk] The focus-triggered navigation control (accessibility fallback) is a new interaction pattern with no prototype validation, unlike the pointer/scroll triggers which were tested. → Mitigation: flag this specifically for a manual keyboard-only pass during Phase 2's accessibility audit (`docs/ROADMAP.md` 2.1A), rather than treating it as proven.

## Migration Plan

1. Replace `lib/tokens.ts` palette and typography tokens (paper/void/ember, Odibee Sans/DM Sans) — full replacement, not additive, per `design-system`'s removed/added requirements.
2. Build the threshold-reveal and mote-scatter components fresh (new components, not modifications of `ExpandingText`/`GraphicTextChapter`, since the underlying mechanism is different enough that adapting the old components would be more confusing than starting clean).
3. Rewrite `app/page.tsx`'s homepage structure: hero, then alternating threshold/chamber sections per doctrine pillar, ending with the existing `CtaBanner` (unchanged position, preserving doctrine-before-conversion ordering).
4. Rebuild `Nav.tsx` for context-triggered visibility (scroll-end / pointer-near-top / focus-triggered fallback), reusing the existing mobile menu toggle and link list.
5. Retire `components/WayfindingThread.tsx`, `components/HeroParticles.tsx`, `components/HeroParticlesGate.tsx`, `components/KineticWordmark.tsx`, and remove their usages.
6. Migrate interior page components (`PageHeader.tsx`, the six route pages) to the new palette/typography tokens only — no structural change.
7. Verify per `openspec/specs/design-system/spec.md`'s reduced-motion and contrast scenarios, and `site-scaffold`'s keyboard/touch navigation scenarios, before merge.

No rollback complexity beyond a normal Vercel deployment rollback — this is a presentation-layer change with no data migration.
